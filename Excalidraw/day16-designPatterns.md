In history, with the implementation of the mouse. Originally the PC just has to wait for inputs from the keyboard. But with the mouse. The program must wait an input from either the mouse or keyboard which the current implementation cannot do because it stalls waiting for keyboard and blocks others ^4cDdXZ3g

It brought complications, the solution was to have events/ inputs

Events drive the software ^5YWmvYfv

Event Driven Programming Skeleton Format:

1. Entry Point
2. Set attributes (OOP)
3. Set virtual function
4. Register the class 
5. Constructor of the class 
6. Event loop

    - Get message object to receive
    - wait for message to arrive in queue
    - if message not process, terminate event loop
    - else, dispatch appropriate function
    - return with status of processing  ^gZEifaPs

Polling vs Event Driven?

- Polling is where the application listens to user input for changes while event driven is when the input calls a function to do something

- Event driven have instant output unlike polling whcich has higher latency. Also polling is less efficient because it consumes CPU cycles when nothing is happening ^Ie2HXWXs

Why avoid blocking calls?
- This is to avoid operations of different threads from blocking one another. Having many blocking calls will stall the program operation cause each instruction waits for the other to finish ^aM8us9YQ

How do you make a queue interrupt safe?
- Make the objects volatile to always listen to user input than cache and also 
- However to solve race conditions, we temporarily disable global interrupts before modifying the queue pointers ^Hjk2l8H9
