Memory Layout

Section Layout
- .text for code & constants
- .bss for uninitialized data
- .stack for stack
- .data for initialized data  ^tGFZNo7N

.text section
- its part of ROM 
- all program functions live here so having the wildcare *(.text*) tells that all script files go here. The .vector is there for the reset handler  ^U6x1JCUi

.bss section
- This is for variables that are uninitialized 
- If a variable is set to 0, it goes here to save space ^rFYjcj2g

.stack section
- this is in RAM
- must reserve space by telling its size 
- location counter tracks the current offset in a memory as sections are added. It increments accordingly 
- ALIGN function  ^eyu1l5th

.data section
- contains static variable when init value at boot
- must load from flash. At boot the reset handler copies the data from flash to ram before main 
- This is possible with the linker using load address and virtual address
- Load Address (LMA) is where the JTAG loader needs the section and virtual address (VMA)  where the section is found during execution
- LMA is address at rest, VMA is address during active  ^JTBjA4tF

MEMORY
{
  rom      (rx)  : ORIGIN = 0x00000000, LENGTH = 0x00040000
  ram      (rwx) : ORIGIN = 0x20000000, LENGTH = 0x00008000
}

STACK_SIZE = 0x2000;

/* Section Definitions */
SECTIONS
{
    .text :
    {
        KEEP(*(.vectors .vectors.*))
        *(.text*)
        *(.rodata*)
    } > rom

    /* .bss section which is used for uninitialized data */
    .bss (NOLOAD) :
    {
        *(.bss*)
        *(COMMON)
    } > ram

    .data :
    {
        *(.data*);
    } > ram AT >rom

    /* stack section */
    .stack (NOLOAD):
    {
        . = ALIGN(8);
        . = . + STACK_SIZE;
        . = ALIGN(8);
    } > ram

    _end = . ;
}

context: the data is not being pushed into RAM from ROM 

The fix: 
- the route in startup.c for the address of source to destination was wrong
- the initial setup of the vector table was wrong, the vector table is a fixed table for specific slots. I made stack pointer in slot 1 even though stack pointer was already in slot 0. And slot 1 was for the reset handler 
- CPU reads slow 1 at reset 
- Next part was the format, the reserved slots were not properly made 
 ^jEEoViCP

If we comment out .data in the copy loop in startup.c, then it will leave the init as garbage data. Not 42 or 0. The reason being in ROM when RAM loses its memory the compiler stores the number in ROM where the _la_data points

When the program runs, it needs to modify "init". It cant be written to flash so "init" is assigned an address in RAM

When the MCU starts, RAM does not automatically clear to 0. The physical memory cells inside SRAM power in random

The .data copy in startup.c looks at ROM (_la_data) where 42 is at. It copies 42 over the variables designated slot in RAM 

If the loop is commented out, it is never copied. The variables address in RAM is untouched meaning it just reads off whatever electric garbage to be sitting in RAM  ^y36ZU6dY

Find init in app.map and how it travels from ROM to RAM:

analyzing this, I can see my 42 value is at _etxt at 0x0800014c. it goes to just the edge after .bss and loadaddr from .data to la_data. This ladata is then used for the address 0x20000004 which is aleady at the ram and assigned to the variable init  ^DxG1erxg

What happens between power-on and main() ?

At bootup, the vector table is initialized. The stack pointer, the reset handler. The reset handler copies data from .data from ROM to RAM. initialize the .bss to 0. Then calls main. Main uses the contents from RAM variables  ^MYVtJDQu

Why must a global initialized to 42 be copied?

It must be copied because RAM does not remember anything. ROM must feed it information to copy to RAM otherwise RAM will give random values to the variable ^pORqsx4c

What goes in .rodata ?

It contains constant values set in main like const int MAX = 10;  ^YRRIizb3
