RREN register allows to config the number of "reload request registers" to request the watchdog counter gets reloaded

There is 8 "reload request registers", by default 1 is enabled 

For the hardware watchdog to get reset, all the enabled "reload request registers" must be written to

Use case for multiple reload request is for different state machines  ^nhefVInb

For this example, use only the first reload request register enabled  ^IEwBHptM

// hardware_watchdog.c
#define HARDWARE_WATCHDOG_TIMEOUT_SECS 10

void hardware_watchdog_enable(void){
    if((WDT->RUNSTATUS & 0x1) != 0){
        // watchdog is already running and cannot be config
        return;
    }
    // Counter reload value - number of 32.768 kHz
    // clock cycles to elapse before a watchdog timeout
    WDT->CRV = 32768 * HARDWARE_WATCHDOG_TIMOUT_SECS;

    // Enable the watchdog peripheral
    WDT->TASKS_START = 0x1;
} ^rDzWLuig

// main.c
static void prv_check_and_reset_reboot_reason(void){
    const uint32_t last_reboot_reason = *RESETREAS;
    // clear any enabled reset reasons
    *RESETREAS |= *RESETREAS;
    // Halt the system on bootup if watchdog reset 
    const uint32_t watchdog_reset_mask = 0x2;
    if((last_reboot_reason & watchdog_reset_mask) == watchdog_reset_mask)
    __asm("bkpt 10");
    }
} ^Eejx1nQ2

This watchdog has a shortcoming, it cannot catch deadlock between tasks. It should monitor that the event loops are making forward progress

This can be achieved by wrapping the hardware watchdog implementation. Instead of calling hardware_watchdog_feed(). Add API task can register with only feed hardware watchdog if all tasks have recently checked in ^2oXgt060

static uint32_t s_registered_tasks = 0;
statuc uint32_t s_fed_tasks = 0;

static void prv_task_watchdog_check(void){
    if((s_fed_tasks & s_registered_tasks) == s_registered_tasks) {
        // all the task have fed or idle
        hardware_watchdog_feed();
        s_fed_tasks = 0;
    }
}

void task_watchdog_register_task(uint32_t task_id){
    __disable_irq();
    s_registered_tasks |= (1 << task_id);
    __enabled_irq();
}

void task_watchdog_unregister_task(uint32_t task_id){
    __disable_irq();
    s_registered_tasks &= ~(1 << task_id);
    s_fed_tasks &= ~(1 << task_id);
    prv_tasks_watchdog_check();
    __enable_irq();
}

void task_watchdog_feed_task(uint32_t task_id){
    __disable_irq();
    s_fed_tasks |= (1 << task_id);
    prv_task_watchdog_check();
    __enable_irq();
} ^HNwNGOjI

Why use a watchdog?
- A watchdog is used to automatically reset a system without user intervention whenever a program stalls ^s2RN4wWS

Independent Watchdog vs Window Watchdog
- IWDG has full independent clock at 40 kHz. It runs on its own and keeps ticking even if the system clock dies
- WWDG is driven by PCLK1 (APB1 bus clock, where it relies on the chip's internal clock tree)

- the pat of IWDG can be done anytime while WWDG has a specific timing window to pat

- IWDG is used for system level safety net while WWDG is for task sequencing & timeing enforcement ^D7JMy04z

Why never kick it from a timer ISR?
- The timer will fire based on raw clock ticks, it will be unaware of the applications actual threads if they are locked up, deadlocked or in infinite loop
- it has false security, if main freezes, the timer interrupt will still trigger every millisecond in the background and pats the watchdog. The system does not reboot
- the watchdog must prove the main loop is working, not just the hardware clock is pulsing ^m3Sala72

How do you measure stack usage without an RTOS?
- we get the address of the stack limit. We then fill the remaining stack bytes that is not used and count them. The total stack is computed by subtracting the end of the stack and the stack limit. The stack usage is them computed by the total stack minus the unused bytes ^EoNrnJ2H

Why do small embedded projects often avoid malloc ?
- because it increase the heap inside the ram. The more it increases, the likelyhood of stack and heap to collide and cause memory overrite causing unwanted bugs ^jK24ybi5
